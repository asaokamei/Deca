# 「~~10年使える~~長く使える」とは？

## PHPのバージョンアップなどは必ず発生する

* 長く使えるとは、バージョンアップ作業で行き詰まらないこと
  * PHP言語の非互換的な変更
  * 依存ライブラリのAPI変更
  * 依存ライブラリの依存性解決 
  * 突発的なイベント（php2shellなど）！
* たまにある機能追加でイライラしないこと
  * それなりに使いやすい
  * 時間が経っても、コードを思い出しやすい

---

# 具体的には？

## 「__銀の弾丸はない…__」

* 標準に寄せる
  * PSR：PSR-3（logger）、PSR-7（http-message）、PSR-11（container）、PSR-15 (HTTP Server Request Handlers)、など
* 標準で足りない部分は独自Interfaceで外部パッケージを抽象化
* 依存性が少ない、有名で、長く運用されそうなパッケージを組み合わせる
  * Slim4、PHP-DI、twig、など。
  * お気に入りのパッケージがあれば、独自アダプターを作成
* InterfaceとAdapter層はユーザーで管理する

---

# Decaの特徴

## 直下のコードに依存する

* `app/`：ユーザーが管理するコード
  * `app/`は`core/`に依存する。
  * ただし`Adapters/`は直接利用せず`Contracts/`を通してDIしてもらう。
* `core/`：パッケージのグルーコードとユティリティ。
  * `Controllers`, `Middleware`など：開発支援・基底クラス
  * `Contracts/`: 規約・インターフェース
  * `Adapters/`: アダプター / グルーコード
* `vendor/`：外部パッケージ


---

# `Core`の管理

## 「ユーザーが`app/`と`core/`を管理する」

* `Core/`のテストもユーザーが管理する。
  * アダプターのテストは変更しない。
  * 外部パッケージのアップグレードによる影響をピンポイントで検知
  * アプリケーション全体のテストよりシンプルで壊れにくい

> ※ パッケージのアップデート後の健全性チェックが容易  
> だからバージョンアップ作業で行き詰まらない

> これがDecaの特徴（自分のFWを育てる）

# 使い勝手も重要

## 「__使い勝手は妥協はしたくない__」

* Symfony/Laravelと似た使い勝手
  * 理想は、内部の挙動を意識しなくても動くこと
* そのためのグルーコードが`core/`
  * 初期インストールの後はユーザー側で管理
  （Decaに依存することも可能）

---

# 保守性とAIについて

## 「__もう全部AIにお任せしよう__」

* AIが把握しやすいサイズのコードベース
* もしライブラリのAPIが変わっても：
  * AIに「このAdapterを新しいAPIに合わせて修正して」と指示
  * `core/` のテストが通れば修復完了！
* 最悪でもパッケージの別ライブラリへの差し替えで対応可能

# Decaの現状

## 「__作り手に依存する部分が大きい__」

* 「Slimで十分かも？」  
  と思ったときの候補。使い勝手の面倒な部分などが対応済み
* オレオレ・フレームワークのスターターキット
  * 「**プロジェクトごと**」に育てるフレームワーク
  * たとえDecaがEoLになっても保守できる構造
* 対応が難しいものをどうする？
  * ORM、Validation、などInterface化が難しい。
  * 認証など、ORMに依存するなど。
  * テンプレートなども依存性が大きい。
